## 2. 改动一：抽事实从"绝对阈值淘汰"改为"Top-K 保底 + 质量分层"（方案 D）

### 2.1 为什么不简单放宽门槛

单文档内"数量"与"质量"是硬矛盾：没有可验证实体的文档凭空造不出高质量 fact。所以正解不是
"在选择时两全",而是**把质量从"二元门槛"换成"连续权重"——数量全保、质量在最终分数里体现**。

支撑这条路的关键洞察：`cg_cvg = cvg_rag − cvg_llm` 是差值结构。

```text
- 低质量=实体不具体、检索命不中 -> RAG/LLM 两边都低、cg_cvg≈0，只【稀释】不【污染】。
- 低质量=实体太泛 -> RAG 可能检索到近邻成员文档，抬高非成员 cvg_rag，【会污染】(v9 §3.1 的
  "检索侧近邻泄漏")。
=> 正因第二种存在，"全选+同权平均"不够；"全选+按特异性加权"才对：太泛实体特异性低 ->
   quality_weight 低 -> 污染贡献被软压。软压比阈值附近的硬切更稳。
```

### 2.2 两层改动

```text
src/attack/entity_extractor.py:
  extract(text, max_entities, guarantee_min=1)
  - 门槛(_passes_hard_gates)降级为"优选":先选过门槛的多样高分实体(primary)；
  - 若不足 guarantee_min，从"未过门槛"候选里按 attackability 补齐(忽略 family 配额)；
  - 每个返回实体标 gate_passed(bool)；新增 _select_topk 保底补齐辅助函数。

src/fact_extraction/fact_extractor.py:
  extract_facts_file(..., guarantee_min_facts=1)
  - 三道阈值(min_importance/replaceability/privacy)与 _is_generic_fact 降级为"优选标准"；
  - 先建候选事实池并标 tier：primary = 过实体门槛 ∧ 过三阈值 ∧ 非 generic；否则 fallback；
  - 选择：primary 按 attackability 降序取 <= max_facts_per_doc；不足 guarantee_min_facts
    再从 fallback 按 attackability 补齐到保底数；
  - 每条 fact 写 quality_weight(=entity_metadata.attackability_score) 与 selection_tier；
  - manifest 新增 facts_by_tier / docs_with_fact_by_group / docs_total_by_group /
    coverage_by_group / zero_candidate_docs。
```

## 3. 改动二：句子定位 bug —— 真正压低覆盖率的元凶（本次最大发现）

### 3.1 诊断

实现方案 D 后第一次重跑，覆盖率几乎没涨（KB 0.326->0.378、True_Non 0.264->0.326），且
`zero_candidate_docs=974`(占 65%)。诊断脚本逐篇核查发现：

```text
docs=1500
  extract() 返回空(真无候选)         : 1
  有候选但实体不在所定位句子(疑似误杀): 973   <- 元凶
  正常可产出                        : 526
失败样例: 实体 '01/25/2000'(偏移239-249) 被错配到句子 'X-FileName: ebass.'
```

### 3.2 根因

`fact_extraction/fact_extractor.py` 的 `_sentence_for_span` 用 `text.find(sentence)` 重新
定位句子位置。邮件头等重复短行会让 `find` 返回**错误的首次出现位置**，于是 [start,end] 容器
判断把实体误配到无关句子；随后"实体必须出现在所定位句子里"的结构性检查失败 -> 整条候选被
误杀。而 `attack/entity_extractor.py` **早已用 SENTENCE_RE.finditer 的正确 match 偏移算好了
`supporting_sentence`**，却被 fact_extractor 丢弃重算。

**这个 bug 在旧代码里同样存在，是 v1~v9 期间覆盖率长期只有 ~32%/26% 的真正原因，与门槛无关。**
方案 D 的调查顺带把它挖了出来。

### 3.3 修复

fact_extractor 直接复用实体已算好的 `supporting_sentence`（缺失时才退回 _sentence_for_span）。

### 3.4 修复后数据（小规模 small split：KB/True_Non/Reserve = 500/500/500）

```text
指标                改造前      改造后
KB_Member 覆盖率     0.326       0.938
True_Non 覆盖率      0.264       0.932
Reserve 覆盖率       ~0.35       0.916
facts 总数           621         2381
zero_candidate_docs  974         107
primary / fallback   —           2366 / 15
selection bias AUC   0.531       0.503   (基本归零)
```

注意：修复后 primary=2366、fallback 仅 15 —— 说明**实体一旦正确定位，绝大多数本就够格**。
即"淘汰率过高"约 70% 是这个 bug 造成，门槛只占小头。方案 D 的保底机制成了安全网而非主力，
但它正确、无害，且把 selection bias 顺带消除。

## 4. 改动三：第 11 步质量加权聚合 + 三口径

### 4.1 数据流（为何不改 07/08/10）

`quality_weight` 在 fact 上(fact_id)。stance row 已带 fact_id（stance_parser 透传），故第 11
步打分时**按 fact_id join facts.jsonl 取权重即可**，无需把权重沿 claim/query/response 一路透传。

### 4.2 三口径（src/scoring/pcv_scorer.py，新增 facts_path 参数）

```text
cg_cvg             文档内各 pair 的 cg_cvg 简单平均(旧口径,保留；下游 shortcut/校准仍用它)。
pcv_score          按 quality_weight 加权平均(方案 D 主分)；权重和为 0 时退回简单平均。
pcv_score_primary  只用 selection_tier=primary 的 pair 的简单平均；无 primary 退回全体简单平均。
```

向后兼容：未提供 facts_path 时所有权重退化为 1.0、tier 视为 primary，三口径都等于简单平均，
此时 pcv_score == cg_cvg（旧单元测试 pcv_score==3.0 仍通过）。pcv_score 的旧"简单平均"语义
按主人意见删除、由加权语义取代；阈值判定 predicted_member_t* 仍基于 cg_cvg 以不改判定尺度。

三口径的用途是**交叉验证 fallback / 加权是否真有用**：三者一致=结论稳健；加权更好=加权有据；
仅 primary 反而最好=fallback 在害结果(则回退偏丢弃策略)。src/evaluation/feasibility.py 的信号
分解已纳入三口径，AUC 并排可见。

## 6. 顶会定位的诚实判断（本次明确，未转向）

```text
- 方案 D 作为"顶会方法卖点"：不合适。它=覆盖率正确性(理应如此) + 逆方差加权(教科书) +
  bug 修复(工程)，是【必要不充分】，撑不起 novelty。
- 方案 D 作为"顶会实验地基/严谨性论据"：合适且必须。它消 selection bias、保覆盖、对低质量
  fact 鲁棒(三口径 ablation)；放进"fact selection & aggregation"小节即可。
- 真正卡顶会的是别的三件事，方案 D 一件都不解决：
  ① 数据集污染(enron 被 victim 预训练见过，cvg_llm AUC=0.606，阴性对照失败)——审稿人会问
     "测的是成员推理还是模型先验"。
  ② 缺 SOTA 正面对比(S2MIA/MBA/RAG-MIA/IA/E-MIA 多为 reserved interface)。
  ③ novelty 定位：真正有顶会相的是 v9 §4.3 —— RAG 的 shadow 几乎免费(re-embed)，故 PCV-MIA
     负担得起 per-example 的 L2(offline LiRA)，而传统 MIA 做 LiRA 要训几百个 shadow model。
- 方案 D 会引来的两个顶会级追问 & 应对：
  (a) fallback 是否人为造数据 -> 用 pcv_score_primary 口径证明结论不依赖 fallback(当前仅 15 条)。
  (b) quality_weight=attackability 是否 data-snooping -> 权重只依赖文档自身特征、与 label 无关、
      未在测试集上调过。
- 当前第一优先仍是用"victim 没见过的私密数据"把【可行性】坐实(让阴性对照回 0.5)，顶会必须盖
  在可行性之上。方案 D 已就位，不必再投入。
```


## C. 第 09 步隐蔽过滤（src/query_generation/stealth_filter.py）

```text

   manifest 增 accepted_pairs / rejected_pairs / pair_rejection_rate；被同伴连累者标 pair_partner_rejected。
C2 危险词误杀：移除过宽的 \bdatabase\b、\bindexed\b（在合同/财报/技术文本里高频，会大量误杀）。
```

## D. 报告层两个 bug（src/evaluation/report_builder.py、mechanism_analysis.py）

```text

   注：这些 fallback 在正常流程根本走不到（pcv_scorer 必产 pcv_score），纯属代码严谨性，不改任何
```
